## 已确认的实现缺口

### 1. 模型步骤的引用校验会接受全部无效引用

位置：`apps/api/app/modules/diagnosis/model_flow.py:116`。

向校验函数传入有效检索来源 `real-1`，模型却引用 `invented-1` 时，函数删除无效引用后仍返回步骤，结果为 `accepted=true, citations=[]`。空引用同样被接受。这样只能保证展示出来的引用 ID 属于检索结果，不能保证输出确有依据，也不能保证引用内容支撑操作。

建议：出现未知 ID 时拒绝输出；针对需要证据支撑的操作，明确无有效引用的降级规则，并增加对应回归。

### 2. 向量服务失败时索引任务会被标记完成

位置：`apps/api/app/modules/knowledge/retrieval.py:34` 和 `apps/api/app/worker.py:46`。

在隔离测试库中模拟向量服务返回失败 `None`，`build_index` 直接返回，Worker 随后将任务标记为 `done`，清空错误及载荷；复现结果为完成任务 1 个、实际写入向量的分块 0 个。BM25 仍可工作，但“可靠任务重试”未覆盖这一类临时向量服务失败。

建议：区分向量功能未启用与已启用但调用失败；后者进入重试或显式降级状态，保留可恢复的任务信息。

### 3. 一键启动没有启动 Worker

位置：`启动项目.bat:12`、`:19`。

脚本仅启动 API 和前端。邮件发送、知识索引和附件异步删除由 `app.worker` 执行，使用该脚本的用户不会自动获得这些后台执行能力。README 已列出单独启动 Worker 的命令，Docker Compose 也定义了 Worker；缺口在一键入口。

建议：一键入口启动并检查 Worker，或明确显示后台任务尚未运行。

### 4. “桌面端”CPU-Z 榜单混入移动处理器

位置：`apps/web/src/data/benchmarkSets.ts:40` 至 CPU-Z 两个数据集定义。

两个数据集标为 `platform: desktop`，但直接使用全部 `rankedLadderCpus`，没有按平台过滤。实际 242 条成绩中有 163 条桌面、79 条移动处理器；例如 Core Ultra 9 285HX 会进入桌面端列表。文案提及移动与桌面功耗差异，但平台筛选与内容仍不一致。

建议：按真实平台拆榜，或将入口明确标为跨平台 CPU 对比。

当前本地配置为 `APP_ENV=dev`、`AUTO_SEED=true`，SQLite、默认开发密钥、非 Secure Cookie、无需强制邮箱验证；Redis 未在这份配置中启用。这符合本地开发定位，不代表已经完成正式运行配置。服务端有非开发环境启动校验；直接沿用当前配置提供公网服务不属于已验证状态。
